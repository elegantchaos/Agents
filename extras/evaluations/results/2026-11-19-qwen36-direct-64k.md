# Qwen3.6 Direct Server: Transport And Throughput Checks

## Outcome

The existing 35B GGUF runs through direct llama-server at 64k with working authentication, preserved-thinking template controls and an Anthropic tool-call/result cycle. Two short generation samples produced **64.09 and 56.81 tokens/second**. These samples each stopped at a 192-token probe cap while still thinking; they measure generation throughput, not answer completeness or coding quality.

Unmodified Claude Code requests failed before inference because the model's Jinja template rejects a system-role message after a user message. A temporary recording relay that moved those embedded system instructions into the leading system field, preserving their text, enabled a **16.065-second** read-only Claude Code tool/result check. This is a qualified transport success requiring normalization, not a demonstrated clean direct replacement for Ollama. No full coding task was run and no generated candidate code was changed.

## Checks

Unauthenticated model-list access returned HTTP 401; authenticated access succeeded. The setup checked that `_ollama` could read the model and write required state while remaining unable to traverse Sam's home, read SSH data or write shared MLX storage.

`/apply-template` retained a historical reasoning sentinel with the configured defaults and removed it when `preserve_thinking` was explicitly false. This positive/negative control establishes actual template behavior. A separate native Anthropic request emitted `read_probe`, accepted its synthetic tool result and reported the exact returned value.

The tiny throughput samples processed 28 and 4 new prompt tokens respectively; the second reused 24 cached tokens. Generation counts were 192 each. Wall times were 3.206 and 3.418 seconds. These are short samples, not sustained benchmarks or a comparison isolating the server from changes in context and sampler.

## Claude Code Compatibility

Claude Code 2.1.281 used only the Read tool, with hooks and external MCP disabled, an isolated persistent session and local authentication. The request-recording relay was authenticated and loopback-only; it did not alter sampling or thinking parameters. Claude.app and global Claude settings were untouched.

The first recording-only attempt encountered HTTP 500 with `System message must be at the beginning.` The same error persisted with `--exclude-dynamic-system-prompt-sections`, and again with that flag plus `--system-prompt-snapshot off`. Stopped only these isolated probe processes after confirming repeated deterministic failures; retained all three attempts separately.

For the final probe, the relay moved embedded system-role content into the Anthropic top-level system field without removing instruction text. Claude then called Read on a synthetic local file and returned exactly `CLAUDE_LOCAL_READ_OK_61382`, with one tool call, two inference requests, no permission denials and normal exit 0. Session: `2c42bd09-46bf-427b-aa38-3a7c4b9eb9c9`. Thinking blocks appeared in the response and the next request's assistant history, despite the CLI's aggregate thinking-token count reporting zero.

The server processed approximately 5k prompt tokens per request: 6.26 and 6.55 seconds of prompt evaluation, with generation around 53–54 tokens/second. Prefix matching was only partial on the second request. Recorded system instructions changed between turns, including an added remaining-token/proactive-style block; that change precedes the otherwise identical first user message and limits prefix reuse. This deserves attention before a long coding comparison. The relay did not remove those instructions to improve caching.

Claude reported a synthetic USD estimate and a 200k context window for the unknown model. Those are not the local bill or server capacity: inference stayed on loopback and `/props` reported 64k. No hosted inference cost was incurred by these calls.

## Retained Evidence And Limits

Preserved 78 evidence files, scripts, API bodies, raw Claude transcripts, unsuccessful calibrations and a server-log snapshot privately at `/Volumes/Models/evaluations/byte-count-v1/Archive/2026-11-19/qwen36-direct-64k/evidence/`, with a SHA-256 manifest alongside it. Credentials remain private and are not included in this repository. The temporary relay stopped after the check; the restricted direct server remains running.

This establishes a promising smaller-context operating baseline, with an identified Claude/template compatibility gap. It does not establish coding correctness, large-context throughput, sustained memory behavior, Desktop routing, reliable instruction/skill adherence or a speed advantage over Ollama under identical settings. No Swift fixture validation was needed because the fixture and candidate source were untouched.
