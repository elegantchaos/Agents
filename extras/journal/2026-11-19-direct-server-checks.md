# Direct Local Server Checks

At Sam's request, tried the existing Qwen3.6 35B GGUF through direct llama-server at 64k with the coding sampler and preserved thinking. Prepared a separate manual-start LaunchDaemon under `_ollama`; Sam ran the administrator command and reported readiness and passing storage-boundary checks. Existing Ollama configuration and Claude.app were left alone. Experiment helpers remain private rather than becoming maintained Agents tooling, consistent with [AgentTools ownership](../decisions/0004-agenttools-supporting-commands.md).

Recorded the [transport and throughput results](../evaluations/results/2026-11-19-qwen36-direct-64k.md). Authentication, historical-thinking template controls and a native Anthropic tool cycle passed. Short generation samples measured 57–64 tokens/second, but both reached their deliberately small token cap while thinking; they are not coding-quality results.

The real Claude Code check exposed a template incompatibility: an embedded system-role message after the user message caused HTTP 500 before inference. Two per-invocation prompt flags did not correct the observed ordering. Retained three failed calibrations, stopping only the test processes. A temporary authenticated recording relay then moved those system instructions into the leading system field without dropping their text. Claude completed a read-only tool cycle in 16.065 seconds. Recorded requests contained no sampler overrides, and thinking returned in the next turn's history. Prefix reuse was limited by changing system instructions; neither the compatibility normalization nor its caching consequences should be hidden in a future comparison.

Preserved 78 private evidence files and a SHA-256 manifest on the Models volume. The relay stopped; the separate direct server remains running without an open terminal. No full coding evaluation, model-file modification, candidate-code repair, global prompt change or hosted inference was performed. A long coding run remains a separate next step after settling the transport profile.

## Upstream Release And Ollama Controls

Checked upstream stable [v1.0.0](https://github.com/ggml-org/llama.cpp/releases/tag/v1.0.0), published 13 November, and newest available nightly [b12532](https://github.com/ggml-org/llama.cpp/releases/tag/b12532), published 19 November. Source inspection found no normalization addressing this failure: the Anthropic adapter preserves embedded message roles and the bundled Qwen template still rejects non-leading system messages. [Issue 27367](https://github.com/ggml-org/llama.cpp/issues/27367) reports this exact Claude/Qwen problem; a maintainer attributes the restriction to the model template, and the issue was closed as stale rather than fixed. A server upgrade alone is therefore not an established remedy. Existing billing-header normalization handles a different source of cache invalidation from the changing environment/token-budget instructions observed here. No release was installed or replayed in this check.

Clarified why direct serving was explored: explicit template parameters, full-history thinking preservation, diagnostics and finer runner controls. Smaller context and the coding sampler do not require leaving Ollama. Its [options](https://github.com/ollama/ollama/blob/v0.40.16/api/types.go) include context, sampling, presence/repetition penalties, threads and GPU layers; its [FAQ](https://docs.ollama.com/faq) documents Flash Attention and global KV-cache precision. The installed version's [Qwen3.5 renderer](https://github.com/ollama/ollama/blob/v0.40.16/model/renderers/qwen35.go), used for our Qwen3.6 model, renders thinking after the most recent real user query rather than preserving it across all historical queries. Direct Jinja `preserve_thinking=true` is a concrete additional control. This source observation is not a runtime verification of Ollama's entire request path.

The direct experiment reused Ollama's bundled llama-server executable; it did not test a newly installed upstream build. The short throughput samples also changed context and sampler from earlier runs, so they establish no independent speed advantage from bypassing Ollama. A matched 64k coding-profile Ollama control would separate those variables before choosing a permanent backend. The earlier suggestion to fix the Anthropic adapter should be reconsidered in light of upstream treating this as a template constraint; a template override or retained Ollama renderer may be simpler than maintaining a server fork.
