## Findings

1. **Should fix, P2: handle the target of an untagged existing draft explicitly.**
   `plugins/baseline/skills/git/references/draft-releases.md:26` gives an edit
   command without `--target`. Step 1 chooses an intended commit and generates
   notes for it; step 2 checks an existing remote tag, which does not cover a
   draft whose tag has not been created. If a draft targets commit A and the user
   asks to update it for commit B, the supplied command updates its notes but
   does not request a target change. The CLI only sends `target_commitish` when
   `--target` is supplied. Step 6 can detect a mismatch after the write, but the
   workflow should avoid making that inconsistent update.

   Require comparison of the existing draft's effective target with the intended
   SHA before editing. When its tag is absent, distinguish its `targetCommitish`
   from a Git tag and either pass `--target <intended-sha>` for an authorized
   target update or stop before changing notes. When the tag exists, retain the
   current tag-commit mismatch stop; changing release metadata cannot move it.

   Evidence: [CLI edit implementation](https://github.com/cli/cli/blob/trunk/pkg/cmd/release/edit/edit.go),
   `getParams` only includes `target_commitish` for a nonempty target;
   [GitHub release API](https://docs.github.com/en/rest/releases/releases#update-a-release)
   defines the field and says it is unused for an existing Git tag. This is a
   source-verified workflow gap; no live release was modified to reproduce it.

2. **Suggestion: make draft state an explicit preflight check.**
   At the same line, the example includes `--draft`. The phrase "For an existing
   draft" already establishes the intended precondition, so this is hardening,
   not a separate proven violation of that condition. State that the agent must
   verify `isDraft` and stop if the matching release has been published since it
   was last inspected. The flag sets draft state; it is not a guard that rejects
   published releases. GitHub's [release API](https://docs.github.com/en/rest/releases/releases#update-a-release)
   documents that `draft: true` makes a release a draft. The CLI fetches a release
   and sends the flag without checking its previous draft state. This closes a
   non-obvious external-state hazard without changing the intended workflow.

3. **Suggestion: point refresh validation at the shared Python rule.**
   `COMMON.md:16` already permanently requires
   `~/.local/share/agents/.venv/bin/python` for Python agent utilities, and root
   `README.md` documents the environment. No new global rule or environment is
   needed. A short pointer in `baseline:refresh`'s verification guidance would
   make that rule easier to encounter during skill checks, including worktree
   sessions. Keep COMMON as the owner; do not add Python runtime requirements to
   the Git skill, which contains no Python scripts.
