# 2026-10-16

## SwiftUI guidance, debugging, and review modes

- In Bookish, every macOS toolbar item flickered whenever a toolbar command button changed availability, and repeatedly at launch. The cause was Commands' `CommandButton`, whose `body` had `if availability != .hidden` as its outermost view; the branch never changed. Finding it took many rounds of builds and manual checks. `performance.md` and `patterns.md` covered conditional structure in general, but `performance.md` had not been read, the `if` was dismissed because its branch never changed, and a reproduction rebuilt from assumptions never contained it. Diff reviews had missed it because `CommandButton` predated the change that first exposed it.
- `swift:swiftui` now has required references (patterns, performance, views, data, api), further references, a Debugging section requiring every reference and an audit of the failing path, including dependencies, before experiments, and a checklist. `performance.md` and `patterns.md` add the specific rule: reusable controls, and toolbar, menu or list-row content, keep a fixed outermost view with any conditional inside a container, with the toolbar flicker as evidence.
- `baseline:standards` gains a Debugging section for every language: read every reference of every relevant skill when tracking down a bug or regression, audit the failing path first, and build reproductions from copies of real code.
- `baseline:review` distinguishes diff and full reviews. A diff review's scope includes code the change newly depends on or places in a new context. After a diff review of a pull request, a full review is offered for each touched package with at most 5,000 source lines, or whose last full review is over 30 days old, predates its last release, or is unrecorded. Full reviews are recorded as journal entries titled "Full Review".
- Baseline bumped to 0.6.0, swift to 0.11.0. The thresholds are Sam's to adjust. Runtime behaviour of the new review modes is untested.

## Temporary files

- Bookish's `.build/tmp/` had grown to 4.9 GB of PR bodies, review folders, logs, scripts and simulator derived data from earlier sessions. `COMMON.md` now says that `.build/tmp/` holds working files only: agents remove their own once a task no longer needs them, and report and offer to clear files left by earlier sessions, since another session may still be using some.

## Whole-codebase reviews

- Sam pointed out that the review skill's UI text described only change and package reviews, though reviewing the entire codebase is wanted. `baseline:review` now gives full reviews two scopes, one package or an entire codebase, and a method for the latter: an inventory with explicit scope, a full review of each package, a cross-package pass for duplication, boundaries, decisions and documentation, and a report listing anything not read in full, so a sampled review is never reported as complete. "Full Review" journal entries name the packages they covered. The UI short description now mentions whole codebases.
- Sam pointed out that a whole-codebase review must consider how everything fits together, since reviewing packages in turn misses duplication across packages and platforms, API and design mismatches, and inconsistent standards. The method now starts by mapping the whole, then reviews the seams between packages and the concerns that cut across them, before reviewing each package in depth with that map in hand. Codebase-level findings lead the report, and a report made only of per-package findings is not a codebase review.
- Walking through how "review PR #N" and "review the codebase" would be handled exposed three gaps, now fixed: a table maps requests to modes and report structures, asking when a request fits more than one; an entire-codebase review over about 10,000 source lines proposes splitting package-depth reviews into separate sessions while the map, seams and whole-codebase passes stay together; and codebase reviews have their own report structure, with Map, Codebase Findings (Seams, Across the Whole) and Package Findings sections.
