# How Much Detail A Design Holds

Sam asked for a better account of the line between design and implementation documentation than "the main concepts and moving pieces, without too much detail". Level of detail turned out to be the wrong axis: a precise data format that other components rely on is design, and a high-level tour of how the code is organised is implementation. The line is commitment, meaning what any conforming implementation must honour.

Sam added two limits that commitment alone misses. A design that holds every implementation-neutral detail can still be so prescriptive that only one implementation could conform. A design with the right content can still be unusable if the detail comes too early.

The records skill's Scope And Boundaries section now opens by stating a design document's primary purpose: communicating the overall shape of the design clearly to its reader, which the other rules serve. It follows with the commitment framing and replaces its single replaceability check with three questions in order: commitment (could the implementation change while this stays true, or would a behaviour-preserving refactor force an edit?), necessity (does anything depend on it? if not, leave it open, and say so where readers might assume a constraint), and placement (does a reader need it to understand the whole?). Progressive Disclosure now says that bulky but necessary contracts go in a detailed subsection of their concept or a linked design document, and the compliance checklist checks for both.

The Design Documents section itself broke its own progressive-disclosure rule: confirmation and naming came before the reader learnt what a design document is for. Its subsections now run from purpose and boundaries, through progressive disclosure, shape, currency and diagrams, to naming, confirmation and the checklist, whose items follow the same order. A one-line pointer at the top keeps the confirmation gate visible.

Design diagrams are now hand-written SVG, not Excalidraw. Bookish's recent SVG diagrams worked well: one file is both source and image, so there is no source and render to keep in step. The Diagrams section describes what those diagrams do: a `<title>` and `<desc>`, a solid background, alt text, a system font and a small palette. Existing Excalidraw pairs stay until they next need changing. The template comments and checklist follow, and the Excalidraw MCP server stays in the shared Codex config but is disabled by default, like Xcode and Figma, so it costs no context until it is switched on.

AgentTools reads only `runtimes/codex/rules`; nothing reads `config.toml.template` or `mcp.toml`, which were both maintained by hand and had drifted apart. `mcp.toml` was the newer of the two, so its server entries, enabled flags and Cupertino tool approvals move into the template, without its machine-local Playwright `cwd`, and `mcp.toml` is deleted. The Excalidraw token moves from a `headers` table, which Codex ignores, to `http_headers`, which the live config uses.

The template then caught up with Sam's live `~/.codex/config.toml`: model, personality, reasoning effort, web search, features, memories, plugin and skill enablement, disabled connectors, MCP enabled flags and desktop preferences. It leaves out what is machine-local or app-managed: notify, marketplaces, trusted projects, writable roots, MCP `cwd` paths, the ChatGPT app's `node_repl` server and its environment hash, path-keyed desktop preferences, one-off UI state and a project's browser origin. Comments note that `agt refresh` and `agt sandbox configure` supply the marketplace and writable roots. Excalidraw is now disabled in the live config as well. Baseline plugin 0.8.39.
